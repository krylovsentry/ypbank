## Задание

Разработать библиотеку (crate) для парсинга/сериализации/десериализации финансовых данных в несколько форматов и отдельный исполняемый CLI (консольное приложение) crate, использующий данную библиотеку.

Примеры файлов и спецификация форматов предоставлены отдельно (см. материалы курса).

## Детали задания

### Крейт Parser

Библиотека, обеспечивающая парсинг и сериализацию форматов.

Реализации парсера **должны использовать абстракции, предоставляемые стандартной библиотекой**, чтобы обеспечить гибкость кода. Не следует жестко привязывать реализацию парсера к конкретному типу источника данных.

Используйте стандартные трейты ввода/вывода — в первую очередь `Read` для чтения и `Write` для записи. Не пишите отдельные реализации для каждого источника (файла, stdin, массива байт и т.д.). Трейты `Read` и `Write` уже реализованы для множества типов.

#### Пример

```rust
struct YPBankBinRecord {
    // Поля структуры, представляющей содержимое записи
}

impl YPBankBinRecord {
    // Парсит из любого источника, реализующего трейт Read
    pub fn from_read<R: std::io::Read>(r: &mut R) -> Result<Self> {
        todo!()
    }

    // Записывает отчёт в любой приёмник, реализующий трейт Write
    pub fn write_to<W: std::io::Write>(&mut self, writer: &mut W) -> Result<()> {
        todo!()
    }
}
```

Использование трейтов позволяет избежать дублирования кода: не нужно реализовывать отдельные парсеры для файлов, stdin, буферов и т.п. Кроме того, сторонние крейты также могут предоставлять свои реализации этих трейтов.

---

### CLI Converter

Консольное приложение, использующее функциональность парсеров из первого крейта.

Парсеры крейта «парсер» принимают в качестве входа типы, удовлетворяющие трейту `Read`. CLI-приложение должно читать данные из файла и выводить результат в `stdout`. Для библиотеки ничего не меняется — она работает с абстракциями, определёнными в стандартной библиотеке, реализованными для типа `File` и доступными в любом Rust-приложении.

За счёт статического полиморфизма (мономорфизации) в итоговый бинарник попадут только те реализации трейтов, которые реально используются.

#### Пример запуска утилиты

```bash
ypbank_converter \
    --input <input_file> \
    --input-format <format> \
    --output-format <format> \
    > output_file.txt
```

---

### CLI Comparer

Консольное приложение, использующее функциональность парсеров из lib-крейта.

CLI Comparer должен читать данные о транзакциях из двух файлов и сравнивать их. Входные файлы могут быть в любых форматах, которые поддерживаются парсерами из lib-крейта. В случае несовпадения утилита должна сообщать, какая транзакция не совпала.

#### Пример запуска утилиты

```bash
ypbank_compare --file1 records_example.bin --format1 binary --file2 records_example.csv --format2 csv
# Output: The transaction records in 'records_example.bin' and 'records_example.csv' are identical.
```

## Требования к результатам работы

1. Данные должны переводиться **из любого из трёх поддерживаемых форматов в любой другой**. Чтение и запись данных должны производиться за счёт трейтов `Read` и `Write` стандартной библиотеки.
2. Код приложения должен быть размещён на **GitHub** (публичный репозиторий).
3. Реализации парсера должны использовать имеющиеся абстракции, поставляемые с языком, для достижения гибкости кода. **Не нужно делать реализации парсера в привязке к конкретному типу данных напрямую.**
4. Крейт для парсинга данных должен быть **отдельным**, а крейты для исполняемых файлов должны **импортировать элементы из lib-крейта**.
5. **Не использовать `unwrap` в крейтах** (допускается только в тестах и примерах).
6. Реализовать **понятные ошибки** и корректно их отрабатывать в коде (собственный тип ошибки с использованием `thiserror` или аналогичных подходов).
7. **Публичные элементы** крейта «Парсер» должны быть покрыты документацией (`///`).
8. Код должен быть покрыт **тестами** (модульными и, возможно, интеграционными).

## Что проверит ревьюер

- **Правильность оформления крейтов** в `Cargo.toml` (зависимости, фичи, workspace).
- **Структуру крейтов по модулям** — наличие файлов `error.rs` или `result.rs` для обработки ошибок.
- **Именование** модулей, функций, методов, структур и трейтов согласно их назначению.
- **Отсутствие дублирования** — применение трейтов `Read`/`BufRead`/`Write` вместо отдельных реализаций для разных источников.
- **Структуру проекта** — библиотека отвечает за чтение/запись/конвертацию, бинарники — только за интерфейс командной строки.
- **Версионирование** — при наличии breaking changes должна обновляться версия библиотеки (semver).
- **Видимость** (`pub`, `pub(crate)`, `pub(super)` и т.д.) — разумное сокрытие внутренней реализации.
- **Покрытие тестами** — достаточное количество юнит- и интеграционных тестов.
- **Отсутствие жёсткой привязки версий зависимостей** (например, `serde = "1"` вместо `serde = "1.0.219"`).
- **Понятные ошибки** — тип ошибки реализует `std::error::Error`, содержит информативные сообщения.
- **Отсутствие злоупотребления клонированием** — эффективное использование заимствований.
